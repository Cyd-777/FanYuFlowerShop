## 一、讨论里为何提到这些外部源（不等于已选型）

这些是业界常见的「植物信息 API」，讨论稿里用来举例「免手打从哪拉摘要」，**不是**本项目已确认方案。

| 来源 | 常被提起的原因 | 对本项目的局限 |
|------|----------------|----------------|
| **维基百科** | 免费、有中文摘要 API、无 Key | 偏百科叙述；**品种级**（如弗洛伊德）常无专条或混在种/属条目；**无**切花养护、花语、场景 |
| **GBIF** | 分类学权威、免费 | 粒度多在 **种/属**；园艺品种（cultivar）常对不上；返回 **自由文本分类**，不是我们的 `taxonomyRef` 公共块 ID |
| **Trefle** | 性状、花期较全 | 要 Key、英文为主、额度有限；鲜切花零售字段仍对不上 |
| **iNaturalist** | 图多、免费 | 偏生态观察；**无**瓶插养护、花语、搭配 |

**技术约束（若将来接）**：小程序需 **云函数代理** 外网，与「用哪些源」无关。

## 二、外部数据能否填满「我们的模板」？

**结论：不能。** 最多是少量字段的 **参考片段**，且置信度因品种而异。

商家表单 `WikiArticleEditForm` 与顾客端结构对齐，核心分三块 + 大量 **公共块 ID**（`taxonomyRef`、`featureRefs`、`careBaseRef` 等）。外部 API **不提供** 这些块 ID。

### 字段覆盖率（粗估）

| 分区 | 代表字段 | 维基摘要 | GBIF | 说明 |
|------|----------|----------|------|------|
| 基本信息 | 种类/品种/icon | — | — | 用户输入 |
| 图鉴 · 块 ID | taxonomyRef、horticulturalGroup、productionRegions、flowerForm、featureRefs | ❌ | ❌ | 须选公共块或内置 default |
| 图鉴 · 文本 | 学名、俗名、育种者、推出年代、命名说明、育种地 | △ | △ | 品种级常缺失；GBIF 多为种名 |
| 图鉴 · 形态 | 瓣数、花径、色泽、茎叶、香气 | △ | ❌ | 维基偶有一句，无结构化 |
| 图鉴 · 区分 | distinguishFrom | ❌ | ❌ | 本店专写 |
| 花期 | bloomVase / bloomSoil | ❌ | ❌ | 切花瓶插天数，外部几乎没有 |
| 养护 | careBaseRef + 换水/修剪/水位/营养 | ❌ | ❌ | 我们是指南图+块；外部是地栽百科 |
| 花语 | meaning、场景、色彩寓意、搭配 | ❌ | ❌ | 花店语义，外部源不提供 |
| 搜索 | aliases、tags、keywords | △ | △ | 可补少量别名 |

**△** = 偶尔有一句，需人工判断，**不能**直接当 L2 正文。

### 与现有内容策略的关系

- 顾客端详文：**103 篇内置 L2 overlay** 优先，已覆盖图鉴/养护/花语主链路。
- 云库 `flower_wiki`：偏 **搜索、别称、无 overlay 时的补位**，不是从零生成 L2。
- 已有 **智能识别粘贴**（`WikiSmartPasteCard`）：从中文网页/百科 **粘贴** 再字段对照 — 与「自动拉 API」是不同路径；粘贴可含花语/养护叙述，但仍需识别规则，且不是全自动。

因此：**外部 API 不适合作为「一键生成完整词条」**；若要用，定位应是「少数字段的候选建议」，且需人工勾选 —— 是否值得做，要先定产品目标。

**替代方案（已采用）**：**大模型提示词 → 智能粘贴** — 见 [智能粘贴 · 大模型提示词](./智库模块-智能粘贴提示词.md)。商家复制提示词、将模型输出贴回 `WikiSmartPasteCard`，字段对照后应用；不依赖外网 API，覆盖度高于维基摘要。
