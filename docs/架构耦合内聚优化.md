# 架构耦合内聚优化

> **状态**：P0/P1/P2（wikiFlowerGoods）已落地 · **待体验版验收**  
> **目标**：降低全应用耦合热点、提升域边界内聚，减少「改一处全链路回归」

---

## 五项问题与优化方案

### 1 · 花卉身份单一真相源不唯一

**问题**：品种归并同时改 `goods`、`flower_wiki`、`categories`、前端 `wikiFlowerGoods`；`LEGACY_VARIETY_MAP` 在云与 TS 各维护一份。

**方案**

| 阶段 | 交付 | 状态 |
|------|------|------|
| P0 | **`shared/flower-identity.json`** 唯一数据源 | ✅ |
| P0 | **`common/flowerIdentity.js`** + 前端 **`utils/flowerIdentity.ts`** | ✅ |
| P0 | `flowerCatalogMerge.js` 改读 flowerIdentity，不再内嵌 map | ✅ |
| P1 | 商品/词条 **稳定 ID**（`kindId`/`varietyId`）作关联主键；展示名变更不 cascade | ✅ resolver |
| P1 | 归并操作收敛为 **`flower merge` 单一入口**（CF action 或脚本） | ✅ `flower.mergeCatalog` + `runFlowerCatalogMerge` |
| P2 | `wikiFlowerGoods.ts` 只读 ID + 缓存 alias，不写死种类名 | ✅ stable `wiki:kind:*` + legacy 兼容 |

**原则**：运行时只认 **`kindId` + `varietyId`**；legacy 字符串 map 仅作迁移兼容层。

---

### 2 · goods 云函数「超级模块」

**问题**：目录 + 库存 + 流水 + 资产 + sharp 图片处理同文件（~1500 行）；任意改动需整包部署。

**方案**

| 阶段 | 交付 | 状态 |
|------|------|------|
| P0 | **`goods/actionRegistry.js`** — action → bounded context 路由表 | ✅ |
| P1 | 同 CF 内拆文件：`catalog/`、`inventory/`、`media/` handlers | ✅ |
| P2 | 可选拆为 **`goods-catalog` / `goods-inventory` / `goods-media`** 独立 CF | 未做 |
| 全程 | 前端 **`services/goods.ts`** 保持 facade，调用方无感 | — |

**库存域边界**：与 [可售数与进货模块](./可售数与进货模块.md) 一致 — 可售数 + 流水，非 WMS。

---

### 3 · 商家鉴权复制

**问题**：`OWNER_OPENIDS` / `isMerchant()` 在 10+ 云函数各写一份，白名单漂移 → silent auth bug。

**方案**

| 阶段 | 交付 | 状态 |
|------|------|------|
| P0 | **`common/merchantGate.js`** — 白名单 + `isMerchant` + `isOwner` + `resolveMerchantActor` | ✅ |
| P0 | order / goods / category / wiki / flower / shop / seedDemo / initDb / notify 迁移 | ✅ |
| P1 | **staff** 改用 merchantGate（保留 invite 专有逻辑） | ✅ |
| P1 | 文档 [云开发模块-数据库](./云开发模块-数据库.md) 指向 merchantGate 为唯一维护处 | ✅ 见架构 doc |

---

### 4 · 缓存 module 隐式联动

**问题**：改 goods 常连带 bump categories；客户端 `cacheKeys` 与 `cache_meta` 无文档化矩阵 → stale。

**方案**

| 阶段 | 交付 | 状态 |
|------|------|------|
| P0 | **`common/cacheInvalidation.js`** — `INVALIDATION_MATRIX` + `bumpCacheEvent()` | ✅ |
| P0 | 前端 **`src/data/cacheInvalidationMatrix.ts`** 与云端矩阵对齐 | ✅ |
| P0 | goods 目录变更 → `goodsCatalog`；纯库存 → `goodsStock` | ✅ |
| P0 | flower 合并 → `flowerCatalog`；wiki → `wikiContent` | ✅ |
| P1 | 客户端 `invalidateCacheModule` 按矩阵批量失效 | ✅ `invalidateCacheEvent` |
| P1 | CI 校验 matrix 与 `cacheMeta.MODULES` 一致 | ✅ `scripts/check-cache-matrix.js` |

**矩阵摘要**

| 事件 key | bump modules | 典型触发 |
|----------|--------------|----------|
| `goodsCatalog` | goods, categories | CRUD / 上下架 |
| `goodsStock` | goods | 出入库、下单扣减 |
| `wikiContent` | wiki, categories | 词条编辑 |
| `flowerCatalog` | flower, wiki, categories, goods | 品种合并 |
| `shopSettings` | shop | 店铺装修 |
| `notifyInbox` | notify | 系统通知 emit |

---

### 5 · 通知与订单/库存同生命周期

**问题**：notify 应是 order/goods 的**反应层**；同事 IM 原型塞在 notify CF 会再次模糊边界。

**方案**

| 层 | 职责 | 状态 |
|----|------|------|
| **写库 + 双发** | `common/bizNotifyEmit.js`（order/goods hook 调用） | ✅ |
| **订阅发送** | `common/subscribeMessage.js`（notify + emit 共用） | ✅ |
| **读收件箱** | `notify` CF：`list` / `unreadCount` / `markRead` / 订阅配置 | ✅ |
| **不做** | `notify.send` 同事互发 — 标记 `@deprecated`，UI 已移除 | ✅ |
| P1 | 定时任务 **`scheduler` CF** | **不做** · 日汇总改订单累加/面板；滞销改销售面板；pending 商家主动盯单；不占云端定时 |

## 模块依赖（优化后目标态）

```
shared/flower-identity.json
        ↓
common/flowerIdentity.js ←→ src/utils/flowerIdentity.ts

common/merchantGate.js  ←  所有 B 端 CF

common/cacheInvalidation.js ←→ src/data/cacheInvalidationMatrix.ts

order/goods  ──→  bizNotifyEmit  ──→  biz_notifications
                      ↓
              subscribeMessage

notify CF  ── 只读收件箱 + 订阅配置（不写业务事件）
```
